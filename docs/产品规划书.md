# 观测台 · Observatory 产品规划书

> 文档版本：1.0 · 讨论稿  
> 编写日期：2026-10-28  
> 对应产品基线：本地 Windows 开发版 0.1.3  
> 面向读者：产品负责人、开发者、设计者及早期测试用户  
> 代码仓库：https://github.com/calabli/observatory

本文以现有源码、项目说明和已确认需求为依据。凡标记为“规划”的能力均不代表已经发布；阶段时长、性能指标与商业方向属于待验证假设。

## 1. 产品概述与核心决策

观测台是一款本地优先的桌面观测工具，帮助频繁使用 AI 编程工具、拥有多台电脑的用户，把 AI 消耗、设备运行情况、网络状态及 Agent 执行过程放在同一个工作台里查看。

产品首先解决“用了多少、花在哪里、来自哪台设备、数据是否可信”，随后回答“为什么慢、哪一段失败、是否与设备或网络有关”。长期形成从费用到调用、从调用到运行环境的排查路径。

产品当前最有价值的基础是 AI 用量采集与多设备汇总，应优先把这两项做准、做稳。性能、网络和调用栈逐步接入真实数据，避免把设计预览误当成可用监控。

### 1.1 已确认的产品决策

| 决策 | 产品要求 |
| --- | --- |
| 独立桌面应用 | 从 CC Switch 的统计能力中独立发展，使用独立数据目录与生命周期 |
| 品牌名称 | 中文“观测台”，英文 Observatory |
| 布局 | 保留紧凑顶部导航，减少窗口层级与重复标题 |
| 视觉 | 参考 CC Switch：黑白灰层级、橙色操作、青色图表，支持深浅主题 |
| 本机与多设备用量 | 在 AI 用量页通过页签切换，采用相同筛选、指标、表格与刷新行为 |
| 同步可控 | 每种应用均可设置是否共享，应用共享清单默认全部勾选 |
| 总开关默认值 | 局域网共享默认关闭；勾选应用不等于已经向网络开放共享 |
| Harness 归属 | DeepSeek Harness 在来源筛选中独立展示和聚合 |
| 图标 | 有可靠来源时使用真实应用图标，选项与选中项保持一致 |
| 数据独立 | 读取原工具数据，不依赖修改原工具配置来完成基础统计 |

### 1.2 产品原则

1. **指标可解释。** 每个数字应能说明来源、计算方式、时间范围和新鲜度。
2. **本地可用。** 单机统计、历史查询与基础诊断不依赖账号或云服务。
3. **逐步披露。** 首页给出结论，详情再呈现 Token、来源质量和诊断过程。
4. **低负担常驻。** 后台采集应有预算、暂停机制和错误退避。
5. **能力真实。** 未接入、无权限、离线和无数据分别展示，不填造数值。
6. **复用已有成果。** 保留 CC Switch 相关代码的来源与许可，复用经过验证的采集和统计逻辑。

## 2. 用户、场景与需求假设

当前以个人开发者和小规模可信设备环境为首要场景。以下画像用于确定优先级，尚未通过用户访谈或市场样本验证。

| 用户类型 | 典型环境 | 最重要的问题 | 成功结果 |
| --- | --- | --- | --- |
| 多工具 AI 开发者 | 同时使用 Codex、Claude Code、DeepSeek Harness、ZCode 等 | 各工具消耗分散、模型名字不一致、费用难对账 | 一页看到可追溯的用量与费用估算 |
| 多设备用户 | Windows 台式机与 Mac 笔记本切换使用 | 设备发现不对称、漏同步或重复累计 | 同一筛选下可靠汇总，明确哪些设备数据已更新 |
| 本地运行与调试用户 | IDE、Agent、编译与多个代理并行 | AI 变慢时分不清设备负载、网络与上游延迟 | 沿时间线查看关联证据并缩小排查范围 |
| Agent 工作流开发者 | 一次任务包含多个模型、工具和子任务 | 调用过程不透明、失败与成本无法归属 | 从一次任务追踪到具体步骤及其指标 |

### 2.1 代表性任务

- 今天用了哪些模型？费用增加主要来自哪个应用和哪台设备？
- DeepSeek Harness 的调用次数与 Token 是否被正确归属？
- 两台设备合计多少？离线电脑的数据停留在什么时间？
- 为什么一个模型调用显示为未知？是源日志缺失，还是解析器尚不支持？
- ZCode 的一次长请求，是首次输出慢，还是整个生成过程长？
- Mac 可以连接 Windows，而 Windows 发现不了 Mac，下一步应检查什么？
- 某次 Agent 任务在哪一步失败？失败前已经消耗了多少？

### 2.2 暂不覆盖的目标

早期版本不承担 AI 网关路由、密钥托管、供应商故障切换、企业计费结算、员工行为审计、远程控制或通用运维平台职责。网络模块不以抓取应用正文、自动修改系统 DNS 或接管代理为基础功能。

对调用行为进行观测不等于执行 Agent；对资源与网络建立时间关联也不等于能自动证明根因。

### 3.2 应用接入分级

| 等级 | 应用 | 当前含义 |
| --- | --- | --- |
| 独立采集 | Claude Code、Codex、Gemini CLI、Grok Build、OpenCode、Pi、MiniMax Code、Antigravity、Kimi Code、DeepSeek Harness、ZCode | 已复用日志采集器；实际覆盖仍取决于工具版本、日志存在性与字段完整度 |
| 导入或对端共享 | Claude Desktop、Hermes、OpenClaw | 可展示导入或共享记录，目前没有独立日志采集器 |
| 未适配来源 | 其他工具 | 显示未支持，可通过后续适配器或标准事件入口接入 |

“应用列表里可选择”不得被描述为“已支持直接采集”。接入状态需要在数据来源页明确展示。

### 3.3 当前重要限制

- 0.1.3 是 Windows x64 开发构建，不能据此宣称稳定版或已验证的跨平台正式发行。
- 当前局域网协议没有配对认证；能够访问共享端口的设备可以读取勾选应用的指标。新配对机制是推广前的关键建设项。
- 费用主要用于估算与趋势分析，不等于供应商账单实付金额。
- 部分耗时来自日志时间估算，不能与精确测量混在一起宣传。
- CSV 当前导出当前页，不是全部筛选结果。
- CC Switch 导入建立历史基线，不是持续双向数据库同步。
- 多设备快照持久化已具备，但不代表所有设备的所有最新记录均已完整到达。

## 4. 产品信息架构

```text
观测台
├─ 总览
│  ├─ 今日用量与近期趋势
│  ├─ 设备及同步状态
│  └─ 异常提示与最近任务（逐步接入）
├─ AI 用量
│  ├─ 本机用量
│  ├─ 多设备汇总
│  ├─ 请求明细 / 详情 / 导出
│  ├─ 价格管理
│  └─ 数据来源与统计口径
├─ Agent 追踪
│  ├─ 任务列表
│  └─ 调用树 / 时间线 / 步骤详情
├─ 设备性能
│  ├─ 实时资源
│  └─ 历史趋势 / 受限的进程信息
├─ 网络诊断
│  ├─ 网络概况：接口、IP、网关、DNS
│  ├─ DNS 与连接诊断
│  └─ 诊断历史
└─ 多设备
   ├─ 发现、配对与连接
   ├─ 共享范围与同步状态
   └─ 设备停用、断开与数据管理
```

通用设置通过固定入口访问，包括外观、刷新、采集、数据目录、备份与关于。价格管理和数据来源继续靠近 AI 用量操作区，避免为次要设置增加顶级导航。

### 4.1 筛选与设备上下文

AI 用量的本机和多设备页签共享时间、应用、供应商、模型与状态筛选语义。新增的设备筛选只决定纳入哪些设备，不改变其余筛选含义。

设备性能和网络诊断每次选择一台设备进行查看。尚未具备远端模块共享时，只能选择本机；不可仅切换标题就显示同一套本机数据。

应用筛选改变后，保留现有清空供应商与模型的行为，防止无效组合造成误读。所有筛选变化重置明细页码，刷新不重置筛选。

目标时间口径：事件时间保存为统一时间戳，默认按查看端选择的时区解释“今天”和日期范围；页面、趋势和导出使用相同时区。日期范围采用起点包含、终点不包含，按该时区的自然日划分，并考虑夏令时。只有日汇总、没有事件明细的历史数据保留原聚合时区和日期，不能精确换算时单独说明，不强行挪入另一个自然日。现有数据是否保留了这些元信息，需在 M1 审计后迁移。

## 5. AI 用量模块规划

### 5.1 页面布局

页面由范围页签、筛选区、同步与采集状态、指标条、Token 构成、趋势、应用分布和请求表组成。布局与现有 CC Switch 风格保持连续。

指标条保留四个主要入口：估算费用、请求次数、总 Token、缓存命中率。点击指标切换趋势，其他组件继续服从同一筛选。表格数据较多时允许区域横向滚动，主页面不横向溢出。

### 5.2 指标定义

| 指标 | 产品定义 | 无法计算时 |
| --- | --- | --- |
| 请求次数 | 当前筛选内经过来源去重的调用记录；历史汇总可能只有计数、没有逐条明细 | 区分 0 与来源不可读取 |
| 总 Token | 新增输入 + 输出 + 缓存读取 + 缓存写入；按来源输入语义归一化 | 未记录字段标记缺失，不把未知补成确定的 0 |
| 缓存命中率 | 缓存读取 ÷（新增输入 + 缓存读取 + 缓存写入） | 分母为 0 时显示“—” |
| 费用估算 | 可定价部分按四类 Token 与有效单价计算，保留金额来源 | 缺价部分标记“未定价”，同时显示可计算部分 |
| 成功率 | 已知状态中的成功请求 ÷ 已知状态请求；展示状态覆盖率 | 全部状态未知时不显示 100% |
| 首 Token 时间 | 请求开始至首输出的时间，区分精确值与日志估计值 | 无可靠依据则显示“未记录” |
| 请求耗时 | 请求开始至结束；排除无法建立对应关系的数据 | 保留估算标记 |

上表是目标产品口径。现有采集器对于缺失字段与状态的表达可能不完全一致，必须先进行字段审计，再逐项迁移，不能仅修改前端标签来宣称已经满足。

四类 Token 仅部分已知时，显示“已知 Token 小计”与缺失字段/记录覆盖情况，不称为完整总量。缓存分母不完整时不输出确定的命中率；混合数据集可仅对字段完整的请求计算，并同时展示其覆盖率。明细、汇总和导出均保留这一质量含义。

### 5.3 统计可信度与未知模型

每条请求目标保留：来源应用、来源设备、原始模型名、规范模型名、计价模型名、时间、Token 字段、费用来源、精确度以及解析器版本。

模型处理顺序：优先采用请求级模型字段；不存在时读取同一请求可可靠关联的响应字段；仍缺失才使用有明确关联的会话元信息。不能只凭该供应商的默认配置推断历史请求模型。

对未识别记录提供以下原因：源日志未提供、模型别名未匹配、日志格式暂不支持、历史迁移字段缺失。用户能看到原始字段并提交脱敏样例；允许人工映射别名，但必须保留原始值和修改记录。

未知模型仍计入可确认的请求和 Token。未知价格不能让整条请求从统计中消失。模型识别率与价格覆盖率分别展示，避免把“有模型名”等同于“费用准确”。

### 5.4 价格维护

目标采用可审计的优先级：明确配置的用户覆盖 > 经验证的价格来源 > 当前内置默认值。同步任务不得覆盖人工锁定的价格。

价格管理显示来源、最近同步、计价单位与生效信息。远端记录保留对端的金额和计价依据，接收端不自动重算。

需新增“价格版本”与明确的重算操作。默认更新价格影响后续新记录和确实缺价的记录；已经有金额的历史记录不静默改价。用户主动重算时先显示范围与预估影响，保存重算版本，支持恢复旧结果。

订阅、赠送额度、套餐折扣和税费会影响实际账单。早期只呈现估算，不承诺账单核销。多币种先保留原币种，未经明确汇率来源和日期不跨币种直接相加。

当前费用实现以 USD 为基础。若接入其他币种，先增加币种筛选与分组金额；费用趋势每次查看一个币种，异常比较也限制为同币种、同估值方式。没有这些能力前，其他币种不得直接并入 USD 指标。

目标区分“来源记录金额”与“按 Token 计算的估算金额”。来源明确且币种已知的记录金额优先作为默认统计值；缺失时才使用计算估算，并显示采用依据。二者不一致时保留差异，来源金额仍不等于实际账单。历史重算只生成估算版本，不覆盖来源金额；选择其他估值方式时，指标、趋势、明细和导出必须同步切换，不能混用后比较。

### 5.5 明细、导出与长期数据

保留当前页导出，同时新增“导出筛选结果”，通过后台分批读取完成，显示数量、进度、取消和失败原因。大数据导出不能在界面线程里一次性加载全部记录。

详情显示完整统计字段与来源质量，不默认保存提示词、响应正文、密钥或工具参数原文。历史汇总无法恢复逐条明细时，明确说明汇总覆盖范围与明细数量差异。

长期保留策略需要区分明细与汇总。删除明细前生成汇总并验证总量一致；清理不删除长期去重依据，避免下次扫描把旧日志重新累计。

## 6. 多设备同步与管理

### 6.1 目标体验

两台电脑各自安装观测台、各自采集本机用量。用户开启共享并授权另一台设备后，可在任一端查看授权设备的缓存汇总；离线设备保留最后成功同步结果，并显示数据截止时间。

多设备汇总是来源明确的快照聚合，不是多端共同写同一 SQLite 文件。接收设备不把远端副本再次共享，避免循环累计。

本机默认纳入多设备汇总且只计一次，“已纳入 N 台”包含本机。规划增加设备筛选后允许显式排除本机；全部设备都被排除时展示未选择设备，而不是显示本机数据。设备身份相同的本机副本不得通过远端连接再次纳入。

### 6.2 三类独立开关

| 控制项 | 作用 | 默认 |
| --- | --- | --- |
| 本机采集 | 是否继续读取某应用的日志 | 已支持来源默认启用，保持当前行为 |
| 向外共享 | 是否允许授权设备获取某应用的本机统计 | 共享总开关关闭；应用清单全部勾选 |
| 纳入汇总 | 是否将某个已连接设备加入当前汇总 | 连接完成后启用，可随时停用 |

关闭采集保留历史；取消共享阻止后续对外提供，并向已配对且可达的接收端同步范围变化；停用远端设备保留缓存但排除汇总。断开设备时解释并执行本机副本删除。

仅靠发送端取消共享，无法保证离线接收端立即删除已经获得的数据。配对协议应提供删除指令与确认状态，同时在界面说明历史副本的边界。

未来性能、网络与 Trace 采用独立模块共享权限，默认关闭，不继承“AI 应用清单默认全选”。进程命令行、网络历史、工具参数不自动随统计共享。

### 6.3 发现与连接

保持自动发现和手动 IP:端口两条入口。设备发现失败时，按步骤显示：本机有效网卡、目标地址、共享服务状态、TCP 可达性、协议兼容性与最近失败原因。

发现需覆盖有线、无线和多网卡环境，并避免把代理或虚拟网卡错误地当成唯一出口。诊断只依据本次可观测结果提示可能原因，不把“没发现”直接断言为防火墙问题。

### 6.4 配对与信任（规划，P0）

新增设备身份、一次性配对码、持久化信任列表和撤销入口。正式配对协议必须同时解决设备认证、传输保护、重放控制和令牌保管；不能只增加一个可复用明文口令。

新协议与现有 CC Switch 兼容接口分开处理。旧协议作为用户主动开启的兼容模式，标记“无配对认证”，默认不将其当成可信设备。配对失败不自动降级到无认证连接。

### 6.5 同步一致性

目标快照包含来源设备标识、数据库世代、递增版本、生成时间、覆盖时间段、共享范围、协议版本和内容校验信息。应用快照需事务化，失败保留旧快照；禁止显示半份更新。

重复导入同一快照不增加总量；较旧版本不能覆盖较新版本。重装、备份恢复或数据库回滚必须能识别为世代变化，给出可理解的替换或保留选择。

跨应用重复采集和跨设备复制日志属于另一类重复风险。没有稳定的源记录标识时，不按“时间相近、Token 相同”自动删重。初期提示可能重叠并允许排除设备或来源；统计去重与业务上同一任务的归属要分开。

### 6.6 多设备页面状态

每台设备显示：名称、系统、连接方式、授权范围、最近可达时间、最近成功同步、数据截止时间、缓存量、是否纳入汇总。

“设备在线”“同步成功”“数据新鲜”是三个不同状态。例如设备在线但本机采集未更新时，不能把同步完成时间作为用量产生时间。汇总区显示“已纳入 N 台 / 有 M 台数据过期”，过期阈值由刷新策略确定。

## 7. 设备性能模块

### 7.1 首期指标

| 类别 | 首期内容 | 明确边界 |
| --- | --- | --- |
| CPU | 整体占用、逻辑核心数、近期趋势 | 不支持的温度和频率显示未支持 |
| 内存 | 使用量、总量、占用趋势 | 明确平台缓存内存口径 |
| 磁盘 | 分区容量、可用空间、读写速率（可获取时） | 不扫描个人文件内容 |
| 网络接口 | 当前上下行速率、累计量、接口状态 | 明确是否包含虚拟网卡与回环 |
| 进程 | CPU/内存排行、进程名与必要标识 | 不默认采集完整命令行和环境变量 |

GPU、温度、电池与设备传感器作为后续适配项，每个平台单独显示支持情况。

### 7.2 采样与保留策略（建议值）

前台性能页默认每 2 秒刷新；后台实时采样可降到每 10 秒。原始高频点建议保留 24 小时，分钟聚合保留 30 天，小时聚合保留 180 天，全部允许调整或关闭。

这些是起始预算，不是已完成行为。必须通过低配置设备上的资源测试决定最终值。总览不能重复启动第二套采样任务。

### 7.3 时间关联

允许从请求时间附近跳转到设备负载区间，展示“同一时间段 CPU 较高”等关联证据。没有应用级采样依据时，不展示“该请求消耗了 X% CPU”的精确归因。

## 8. 网络监控与诊断模块

### 8.1 网络概况

显示当前有效接口、局域网 IPv4/IPv6、默认网关、DNS 配置、接口流量与代理环境提示。字段由系统可用接口读取；权限或平台不支持时单独标记。

公网 IP 查询为主动探测，会向外部服务发送请求，需在设置中列明目标与频率。默认不启动持续外部探测；IP 归属与网络质量信息属于辅助数据，不能据此保证服务可用。

### 8.2 诊断任务

| 任务 | 用户输入 | 展示结果 |
| --- | --- | --- |
| DNS 查询 | 域名、系统 DNS 或用户指定服务器 | 返回地址、耗时、错误类型与执行时间 |
| TCP 连通性 | 主机与端口 | 连接成功/超时/拒绝及耗时 |
| HTTPS 探测 | 用户明确选择的地址 | DNS、连接、TLS、首响应等可实际测量阶段 |
| 局域网设备检查 | 已保存设备地址 | 端口可达、协议握手与共享范围状态 |
| 多目标对比 | 用户保存的少量目标 | 相同探测策略下的时延、失败率与样本数 |

探测字段无法拆分时显示整体耗时，不伪造阶段分解。高权限抓包、路由追踪或 ICMP 支持作为独立能力评估，基础功能不要求管理员权限常驻。

### 8.3 诊断边界与风险控制

默认采用低频、短超时和有限并发，禁止自动扫描整个公网地址范围。用户输入的自定义探测目标在本机直接执行，不作为云端请求代理。

在结果中区分配置读取、单次探测与持续监测。单次失败只能说明该时间点、该路径的观察结果。若仅检查环境变量而未读取系统完整代理配置，界面须明确显示覆盖范围。

诊断历史可能暴露内网拓扑和服务域名，默认本地保存、支持清理，并且不自动加入局域网共享包。

## 9. Agent 追踪与调用栈

### 9.1 产品目标

展示一次任务的步骤结构、时间消耗、调用状态和模型用量。用户能从任务找到失败步骤，也能从费用记录反查可可靠关联的任务。

产品中的“调用栈”采用任务树与时间线表达异步、并行和子任务关系。不能将普通日志的排列顺序直接当成真实父子调用关系。

### 9.2 数据模型与来源

| 对象 | 关键字段 | 作用 |
| --- | --- | --- |
| Task | 稳定标识、标题、来源、设备、开始/结束、状态 | 用户可理解的一次工作 |
| Trace | 追踪标识、来源、协议与关联质量 | 汇集一次执行过程 |
| Span | 标识、父标识、类型、名称、开始/结束、状态 | 模型、工具、子 Agent 等步骤 |
| Event | 时间、事件类型、脱敏摘要 | 重试、取消、错误与检查点 |
| UsageLink | 请求标识、Span 标识、关联依据 | 连接现有统计记录，防止双计费 |

先选一个真实可获取父子关系的来源做闭环，再扩展适配。标准追踪事件接入与工具专属适配器均可评估，但具体协议、字段与兼容版本需要单独技术设计，不在本规划中视为已完成支持。

### 9.3 页面设计

任务列表按设备、应用、时间和状态筛选。任务详情左侧为可折叠调用树，中间为时间线，右侧为选中步骤的状态、指标和脱敏事件。

支持定位失败、查看重试、展开子 Agent 和筛选模型调用。长任务逐步加载；未结束任务标记进行中，缺失结束事件标记不完整。

### 9.4 费用与耗时归属

模型请求是可计费用量的基本单位。Span 上的费用是对已关联请求的引用或聚合，不向全局用量再次插入一份副本。父级聚合费用不与子级费用相加。

并行任务的总耗时采用起止时间差，不能把全部子步骤耗时相加。存在重叠区间时，关键路径与资源占用仅在数据足够时计算。无法可靠关联的请求保留为“未关联”，不使用模糊推断制造完整调用树。

跨设备关联同时保存设备时钟偏差或不确定性；时间证据不足时使用相对时间和告警，避免错误排序。

## 10. 总览与异常提示

总览优先呈现已经接入的真实能力：今日费用估算、请求、Token、采集健康度、已纳入设备及同步新鲜度。未接入性能或 Trace 时，用接入提示替代示例曲线。

后续可增加：费用较近一段基线增长、模型识别下降、持续采集失败、设备长时间未同步、资源持续超阈值、DNS 或连接持续失败。

异常提示首期采用明确规则，显示触发条件、持续时间与证据。费用异常按相同时间跨度比较，并明确缺价比例；数据不完整时不触发看似精确的增长结论。

桌面通知按类别独立开启，默认保守；相同异常合并通知，恢复时可选择提醒。早期不引入跨组织通知、自动处置和复杂规则编排。

## 11. UI 与交互规范

### 11.1 风格约束

- 保留现有紧凑顶部导航与系统窗口标题栏，应用内部不再放一条重复的模拟标题栏。
- 橙色表达主要操作与选中强调，青色用于主要趋势，其他颜色表达明确数据类别与状态。
- 表格、菜单、弹窗、空状态和筛选器采用统一组件，深浅主题共用结构。
- 图标使用来源可追溯资源；没有官方资源时采用一致回退，并记录后续替换项。
- 使用系统字体与现有信息密度，优先保证中文、金额、日期与数字可读。

### 11.2 状态与反馈

每个数据区域至少覆盖加载、成功、空数据、无权限、暂不支持、采集失败和缓存过期。刷新期间可保留旧数据，并显示正在更新；失败不能让旧数据看起来像刚更新。

取消共享、停用设备、断开设备、清理本机历史分别采用不同说明。会删除不可恢复数据的操作展示范围和后果；普通筛选、刷新和可逆设置立即生效。

### 11.3 键盘与可访问性

应用菜单支持方向键、Home/End、文字定位与 Esc；所有主要操作可通过键盘完成。图表提供数字摘要，颜色不作为唯一状态信号。界面遵守系统减少动画偏好。

桌面以 820px 最小宽度为正式验收基线；更窄浏览器布局作为开发预览兼容项。表格允许内部滚动，弹窗不超出可视区。

## 12. 技术与数据架构规划

### 12.1 保留现有技术主线

前端继续使用 React、TypeScript、Vite 与查询缓存；桌面宿主采用 Tauri 2；采集、同步和聚合由 Rust 承担；SQLite 负责本地持久化。生产程序直接调用本地核心，不依赖 Node 服务常驻。

不为新增模块立即重写现有统计内核。先统一来源契约与后台任务管理，再将性能、网络、Trace 作为独立服务接入。

```text
桌面 UI：总览 / AI 用量 / Trace / 性能 / 网络 / 设备
                         │
                  本地命令与事件接口
                         │
      ┌──────────────────┼──────────────────┐
      │                  │                  │
  采集与后台调度     查询与聚合服务     配对与同步服务
      │                  │                  │
  工具适配器 / 系统采样 / 网络探测 / Trace 接入
                         │
         本地 SQLite、价格版本、设置与诊断日志
```

### 12.2 统一来源契约

每个适配器声明应用标识、支持版本、采集方式、字段覆盖、精度和权限需求。结果包含新增数、更新数、忽略数、错误和游标，支持暂停、取消与重试。

日志格式变化应隔离在适配器内，单个来源失败不阻塞其他来源。对完整性不确定的数据保留质量标记，禁止用默认值伪装成完整数据。

### 12.3 数据治理

数据拆分为：本机原始统计、历史汇总、远端快照、性能时序、网络诊断、Trace 事件、价格版本和设置。来源设备与数据类别必须可追溯。

数据库迁移具备版本号、迁移前备份和失败恢复；升级失败不覆盖旧库。多个模块共享后台调度与数据库访问机制，避免重复扫描和高频全表查询。

备份应覆盖数据库与必要配置，并说明是否包含信任凭据。恢复到另一台设备时生成新的本机身份，不能复制身份后同时在线。凭据备份与普通统计导出采用不同处理。

### 12.4 隐私与本地控制

默认不采集提示词、响应正文、API 密钥、完整命令行和环境变量。错误日志需要脱敏，用户导出诊断包前能预览内容与范围。

计划不依赖第三方行为分析。早期成效通过本机健康报告、明确的测试数据及用户自愿反馈验证；若未来引入遥测，另行设计可选开关、字段清单和保留策略。

数据目录、磁盘占用、保留策略、导出、备份和清理在统一设置中可见。隐藏后台共享状态不可接受，用户应随时知道共享是否开启以及授权对象。

## 13. 版本路线与实施顺序

以下是建议里程碑，按验收通过进入下一阶段。可并行开展设计与研究，但关键数据契约必须先稳定。预估以一名主要开发者持续投入、具备 Windows 与 Mac 测试设备为前提，不构成发布日期承诺。

| 阶段 | 建议版本 | 工作包 | 完成条件 | 粗略投入 |
| --- | --- | --- | --- | --- |
| M0：工程基线 | 0.1.x | 整理源码、许可、文档、忽略规则；推送仓库；建立 CI；整理开发构建与正式构建区别 | 新环境按文档可构建，测试结果可追溯 | 3–5 人日 |
| M1：可信 AI 用量 | 0.2 | 字段质量、未知模型诊断、口径审计、价格覆盖、完整筛选导出、迁移与备份体验 | 核心统计与历史数据无重复、无静默丢失 | 10–15 人日 |
| M2：可靠多设备 | 0.3 | 配对与传输设计、范围管理、快照世代、同步健康、多网卡与跨平台验证 | 两台真实设备双向同步、重试与撤销均通过 | 10–20 人日 |
| M3：真实设备性能 | 0.4 | 本机采样、趋势、保留、资源预算；总览移除相关示例值 | 指标真实、后台开销符合预算、权限受限可降级 | 8–12 人日 |
| M4：网络诊断 | 0.5 | IP/DNS 配置、主动探测、局域网连接诊断、历史与目标管理 | 能重现并解释典型 DNS、端口与连接失败 | 8–12 人日 |
| M5：Agent 闭环 | 0.6 | 先接入一个来源的真实任务树、时间线、错误与请求关联 | 同一任务可追踪且不重复计费，缺失关系正确呈现 | 15–25 人日 |
| M6：稳定发行 | 1.0 候选 | 跨平台打包、升级回滚、持续运行、文档和问题收敛 | 满足统一稳定性与数据兼容门槛 | 10–15 人日 |

各阶段投入包含开发与基本测试，不含签名账号办理、外部接口等待、未知日志逆向等不可控时间。实际排期在 M0 后依据依赖清单重新估算，不把各行简单相加当作交付承诺。

### 13.1 下一轮优先事项

1. 整理本地项目并推送新仓库，保留许可与来源清单，排除构建产物、真实数据库和临时日志。
2. 建立前端检查、Rust 核心测试及 Windows/macOS 构建验证，明确开发版与正式包命名。
3. 为来源完整性、未知模型和未定价记录提供可见状态，修正统计口径中的缺失字段表达。
4. 编写同步协议设计并完成配对原型，然后做 Windows 与 Mac 的双机验证。
5. 将总览的预览区域逐项替换为真实数据；尚未完成的模块保留清楚的“预览”标识。

### 13.2 延后事项

公网中继、账号体系、云存储、团队工作区、远程执行 Agent、完整账单核销、自动根因分析、插件市场和移动端均放入候选池。只有核心数据可信、同步可靠并且有明确使用需求后才进入排期。

## 14. 验收标准与质量门槛

### 14.1 功能验收

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| A01 | 同一日志重复扫描、重启后再扫描 | 请求数与 Token 不重复增加 |
| A02 | 历史导入后继续原生采集 | 保持基线正确；歧义合并明确阻止，源库不被写入 |
| A03 | 输入 Token 已含缓存的来源 | 归一化后四类合计正确，不双算缓存 |
| A04 | 缺模型、缺价格、缺状态、缺耗时 | 分别说明缺失原因，可确认指标仍计入，不伪造完整值 |
| A05 | 同样筛选分别查看本机与多设备 | 汇总等于明确纳入的本机与远端范围，显示过期与缺失设备 |
| A06 | 同一远端快照重试、失败、乱序到达 | 重试不累计、失败不半更新、旧版本不覆盖新版本 |
| A07 | 关闭来源、取消共享、停用与断开设备 | 各操作按文档执行，数据保留或删除范围清楚 |
| A08 | 新设备配对与撤销 | 未授权设备不能读取新协议数据；撤销后访问失败 |
| A09 | Windows 与 Mac 的有线/无线、多网卡环境 | 发现可用或能明确手动连接；失败诊断有具体证据 |
| A10 | 价格同步与手动覆盖 | 不静默覆盖锁定价格；历史重算可追溯 |
| A11 | 导出全部筛选结果 | 数量、筛选、时间口径一致；支持取消；防止表格公式注入 |
| A12 | 并行 Agent 与父子步骤 | 全局费用只计一次，任务耗时不等于并行子步骤累加 |
| A13 | 性能或网络权限不足 | 其他模块可用，不显示假数值，给出能力说明 |
| A14 | 数据库升级或进程异常退出 | 能恢复到完整状态，旧版数据有备份与明确兼容提示 |

### 14.2 性能与稳定性目标（待基准验证）

拟以 4 核 CPU、16GB 内存、SSD、10 万条用量明细和 3 台设备缓存为首轮参考环境：常用聚合查询 P95 不超过 1 秒，分页查询 P95 不超过 500ms，进入界面优先展示缓存而不等待全量扫描。

后台空闲平均 CPU 目标低于 1%，常驻总内存目标低于 250MB，需分别测量 Windows 与 Mac 并据实调整。性能采样、日志扫描和同步同时工作时，应报告额外开销与峰值，而非仅测空白页面。

稳定性验收包括至少 72 小时运行、睡眠唤醒、网络切换、设备离线重连、数据库写入中断和大量历史数据首次导入。性能目标未达成时先调整采样与查询策略，不牺牲数据一致性。

### 14.3 发布门槛

正式候选版本不得遗留已知的数据重复、金额静默改写、迁移丢失、越权共享和源数据库被修改问题。功能预览不得混入真实统计总量。

每次发布附版本、平台、构建来源、校验值、迁移说明、已知限制和回退说明。Windows 与 macOS 分别验证；未验证的包不标为稳定支持。自动更新的渠道、签名和回退策略需单独验收后启用。

## 15. 成效指标与验证方式

产品成效优先衡量“数据可信且能完成任务”，不以收集更多用户行为作为前提。

| 指标 | 定义 | 验证方式 |
| --- | --- | --- |
| 首次可用率 | 已安装支持工具且存在可读日志的测试环境中，首次接入成功比例 | 固定测试矩阵与自愿反馈，分别记录权限与版本问题 |
| 模型识别覆盖率 | 原始记录存在有效模型线索时成功归属的比例 | 来源样例集；与源字段本身缺失分开统计 |
| 价格覆盖率 | 可识别 Token 请求中具备适用价格的比例 | 显示分母、未定价请求与 Token 占比 |
| 同步正确性 | 预设双机数据集的重复、漏计、乱序错误数 | 自动化快照测试与真实设备验收 |
| 查询体验 | 参考数据量下聚合与分页响应时间 | 本机基准报告，不依赖上传真实记录 |
| 排障有效性 | 给定 DNS、连接和负载故障时是否能找到相关证据 | 场景任务测试及用户反馈 |
| 常驻成本 | 空闲、扫描、同步与采样的 CPU/内存/磁盘占用 | 各平台持续运行报告 |

在没有真实样本前不预设活跃用户或转化率结论。若后续评估留存，使用自愿参与的测试用户访谈或可选统计，不静默上传应用与设备明细。

## 16. 主要风险与应对

| 风险 | 影响 | 应对与排期 |
| --- | --- | --- |
| 工具升级改变日志格式 | 模型未知、漏采或重复 | 适配器版本与样例集，来源健康状态，M1 起持续维护 |
| 历史汇总与明细重叠 | 总量无法可信合并 | 保留基线契约和歧义拒绝，提供备份与独立目录方案 |
| 多端复制同一源日志 | 跨设备双计 | 保留来源标识，提示重叠，证据不足时不自动模糊删重 |
| 价格别名与来源变动 | 费用估算失真 | 原始/规范/计价模型分离，价格版本与覆盖率 |
| 发现不对称或代理干扰 | 用户误认为数据没采集 | 多网卡探测、手动连接与分步诊断，M2 |
| 旧同步协议无认证 | 指标向可达设备暴露 | 默认关闭，明确兼容模式，先完成新协议再扩大分发 |
| 高频监控消耗过高 | 影响开发环境 | 共享调度、降采样、保留上限和取消机制，M3 |
| Trace 数据关系不完整 | 生成错误调用树和成本 | 真实标识优先，保留未关联，不做无依据推断，M5 |
| 范围持续扩张 | AI 核心质量下降 | 每阶段以验收为门槛，候选功能不直接进入主线 |
| 品牌图标与复用代码来源不清 | 发布时难以审查来源 | 保留许可、注释和资源来源记录，公开发布前完成材料核对 |

## 17. 发行、维护与后续决策

当前建议采用本地桌面与 GitHub 分发的方式服务早期用户。开发构建可快速验证界面；稳定渠道必须具备可重复构建、平台验证与数据兼容说明。

商业化暂不作为当前阶段前提。账号、云备份与团队协作会显著改变同步与隐私模型，应在获得实际需求后另立规划，不先行建设收费和账号基础设施。

仍需在对应阶段确认：

| 决策项 | 当前建议 | 最晚确认时间 |
| --- | --- | --- |
| macOS 支持范围 | 首先选定实际可测试的架构，再扩展 | M0 构建矩阵确定前 |
| 正式版签名与更新 | 先人工下载升级，后加入可回退更新 | M6 前 |
| 新配对协议与旧协议关系 | 默认新协议；旧协议仅显式兼容模式 | M2 实现前 |
| 明细与监控保留时长 | 使用建议默认值，允许用户修改 | M1/M3 数据清理功能前 |
| 首个 Trace 来源 | 选择可获取稳定父子标识且便于验证的工具 | M5 开始前 |
| 仓库是否公开 | 当前私有，发布意图明确后再决定 | 首次公开发行前 |
| 完整导出与备份格式 | 分开统计导出和可恢复备份，明确版本 | M1 实现前 |
